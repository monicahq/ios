# Monica iOS

The iOS version of the Monica web app ([monicahq/monica](https://github.com/monicahq/monica),
usually checked out next to this repo in `../monica`). Swift, SwiftUI. The Android app
([monicahq/android](https://github.com/monicahq/android), in `../android`) is a separate project
with the same goals.

- Goal: every feature of the web app over time, plus mobile-specific ones.
- The server is the source of truth. The app uses only its JSON API (`/api/v1`, Sanctum tokens,
  OpenAPI at `/docs/api/v1/openapi`). Missing endpoint? It is added to the Monica API first.
- Same concepts and words as the web app (account, vault, contact, reminder, template...).
- Before specifying a feature, read how the web app does it: screens, `routes/api.php`,
  `resources/docs/api` and wording in the Monica repo. When the Android app already has it, read
  its spec in `../android/specs` too.

**The rules live in `.specify/memory/constitution.md`. Read it before planning or writing code.**
Summary of what it demands:

1. **Simple**: simplest correct code. No abstraction, package or target without a concrete need.
2. **Official Apple practices**: SwiftUI + `@Observable` `@MainActor` view model exposing one
   `state` (UDF), stateless screen views, repositories as single source of truth, Swift
   concurrency with injected dependencies, strings in the String Catalog, no `!` / `try!`.
   See `docs/architecture.md`.
3. **Unit tested**: every view model, repository and non-UI type has Swift Testing tests in
   `MonicaTests`, using fakes. Bug fixes start with a failing test. See `docs/testing.md`.
4. **UI tested**: every screen has XCUITest tests for each state and main interaction.
5. **Native only**: no KMP, Compose Multiplatform, Flutter, RN or WebView UI. Android is separate.
6. **Multilingual**: every text in the String Catalog; English source and fallback, French too.
7. **Accessible (mandatory)**: WCAG 2.2 AA on mobile, accessibility audit in UI tests, VoiceOver
   checked. See `docs/accessibility.md` and the `accessibility` skill.

## Stack
- Xcode project generated by XcodeGen from `project.yml` (never commit `Monica.xcodeproj`;
  run `xcodegen generate` after pulling or changing `project.yml`)
- XcodeGen, SwiftFormat and SwiftLint pinned in `mise.toml` (`mise install`)
- `com.monicahq.ios`, iOS 18 minimum, iPhone, Swift 6 language mode, warnings are errors

## Before considering a change done
Follow the `definition-of-done` skill. In short:
```sh
xcodegen generate && swiftformat . && swiftlint --strict
rm -rf build/unit-tests.xcresult
xcodebuild test -project Monica.xcodeproj -scheme Monica \
  -destination 'platform=iOS Simulator,name=iPhone 17' -only-testing:MonicaTests \
  -resultBundlePath build/unit-tests.xcresult
scripts/check-coverage.sh build/unit-tests.xcresult   # non-UI line coverage of at least 80%
xcodebuild test -project Monica.xcodeproj -scheme Monica \
  -destination 'platform=iOS Simulator,name=iPhone 17' -only-testing:MonicaUITests   # when UI changed
```
CI (`.github/workflows/ci.yml`) runs all of these plus debug and release builds.

## Commits
NEVER commit or push to `main`: always a dated branch and a pull request (enforced by a GitHub
ruleset and `.claude/hooks/block-push-to-main.sh`). Follow the `commits` skill: Conventional Commits `type(scope): sentence`, branches
`YYYY-MM-DD-name`, and NEVER mention Claude, AI or an assistant in commits, PRs or comments
(no `Co-Authored-By` trailer).

## Skills
- `definition-of-done`: checklist before every commit and PR
- `commits`: commit messages, branches, pull requests
- `tests`: how to write unit and UI tests
- `accessibility`: accessibility rules for every screen; agent `accessibility-reviewer` reviews a change
- `feature-documentator`: keep `docs/FEATURES.md` up to date after every feature
- `take-screenshot`: capture the app on a simulator for pull requests
- Spec Kit extensions: `speckit-bug-*` (bug triage), `speckit-assess-*` (evaluate an idea
  before specifying it), `speckit-archive-run` (archive a merged spec), `speckit-companion-*`

## Workflow
Spec Kit: `/speckit-specify` → `/speckit-clarify` → `/speckit-plan` → `/speckit-tasks` →
`/speckit-implement`. `/speckit-specify` always starts with the `speckit-branch-start` hook, which
updates `main` and creates a `YYYY-MM-DD-name` branch from it (local extension in
`tools/spec-kit/branch`). If it refuses (uncommitted changes, existing branch), stop and ask. Specs go in `specs/`. Update `README.md` / `docs/` when a feature changes
how the app is built, configured or used.
